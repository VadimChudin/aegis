## Runtime архитектура
В проекте сосуществуют legacy AI Paper/Python ai_setup на 127.0.0.1:11434 и новый Rust LocalRuntime на 127.0.0.1:11435. Проверяется как актуальный unified observer UI, так и legacy-путь; ошибки одного не автоматически относятся к другому.

## Найденные дефекты и исправления
Раздел будет дополнен результатами независимых проверок и повторных тестов.

### Python legacy AI Paper: подтверждённые и исправленные дефекты
1. Чужой процесс Ollama на 11434 мог ошибочно считаться проектным runtime с готовой моделью, либо получать pull модели в другое хранилище. Теперь legacy setup явно отклоняет уже работающий сервис; перед повторной установкой требуется остановить его. Проект не завершает чужой процесс автоматически.
2. Неверная структура ответа /api/tags могла считаться здоровым сервером либо вызвать необработанную ошибку типов. Добавлена проверка формы ответа.
3. Остаточный общий *.part блокировал retry и удалялся чужой попыткой. Каждая загрузка теперь использует собственный временный файл.
4. Объём потокового скачивания не ограничивался заявленным размером release. Добавлена проверка размера до записи сверх лимита.
5. EOF pull без терминального success мог приниматься как успешная загрузка. Теперь обязательны success и валидные события прогресса.
6. Процесс мог умереть во время health probe, но считаться готовым. После проверки API проверяется живость процесса.

Новые проверки преобразованы родительским агентом в стандартный unittest (без зависимости pytest), чтобы они действительно выполнялись существующим CI. После исправлений: 69 unittest tests, все проходят, включая запуск и завершение лёгкого подставного HTTP-сервера в отдельном процессе. Это не настоящий Ollama/Qwen.

Смежная подтверждённая проблема: legacy ai_setup_model игнорирует результат ensure_server после завершения installer, сохраняя ready при неудачном restart. Проверка Rust-пути продолжается.

### Rust runtime и Tauri commands
Исправлены: ложный успех живого, но неготового процесса legacy; подавление ошибки запуска после установки; зависший setup_busy при ошибке разрешения пути; несоответствие фактической длительности polling заявленному таймауту; оставшийся процесс после неудачного старта; прекращение Unix leader без завершения игнорирующих SIGTERM model runners; устаревший ownership в статусе во время установки/inference; принятие HTTP error bodies за downloaded/loaded; отсутствие config blob и неправильный размер layer blob при проверке скачанного кеша. Готовность теперь требует успешного version JSON с непустой версией; failed start очищает управляемый процесс для retry. Cloud-only legacy step больше не требует локального сервера. Скачанные файлы проверяются по точному размеру manifest и присутствию config; полноразмерный SHA-256 весов при каждом status не вычисляется.

### UI
Тестами воспроизведены 11 ошибок на исходном UI. Исправлены: Start Paper/Money по устаревшему статусу после failed refresh; локальные Install/Start/Ping/Ask при недоступном статусе; восстановление legacy настроек после повторного открытия панели; несогласованное блокирование Start/Step при ошибке; потеря диагностического результата ai_test; выбор неверного брокера при закрытии Paper-позиции; неправильная подсказка legacy endpoint. Stop не блокируется новым флагом statusUnavailable; ограничения busy/ownership остаются прежними. JS-тесты используют Node VM/минимальный DOM/stub IPC, а не настоящую desktop E2E.

### MT5 — две high-severity ошибки, воспроизведённые на fake broker
- Переключение login/server во время order_check позволяло отправить fake ордер на другой счёт и записать его в ledger первоначального счёта. Bridge теперь привязан к account identity после connect и отклоняет смену до reconnect.
- Новый realized loss во время order_check не перепроверялся перед order_send. При инъекции loss $60 и balance $940 прежний код отправлял ордер несмотря на 5% лимит ($47). Перед отправкой повторно проверяются разрешения и существующая политика daily loss; недоступная история блокирует отправку.
Добавлены 6 regression methods, включая subtests. Это сокращает окно между проверкой и отправкой, но не делает внешнее состояние терминала атомарным.

## Что остаётся нерешённым / требует отдельной проверки
1. Medium: reduce idempotency привязан к ticket/fraction, а не уникальному решению. Два разных намерения уменьшить позицию на 50% приводят к 0.08 → 0.04 → 0.04, второе получает cached filled. Не исправлено: требуется согласованный decision/intent id через Rust/Python интерфейс и отдельные тесты на неоднозначные результаты. Не рекомендуется применять повторные частичные выходы до этого исправления.
2. Legacy customized local_url может отличаться от управляемого порта 11434. В этом PR не выполнялась миграция двух runtime и настроек.
3. Длительная установка не отменяется busy-gated Stop; cleanup после уже reap-нутого неожиданно завершившегося Unix leader требует дополнительной проверки.
4. Observer provider requests не используют legacy daily/monthly cloud budget. Это существующее документированное ограничение; платные вызовы в аудите не выполнялись.
5. Реальный Qwen/GPU/RAM/OOM, Windows MT5, установщики Windows/macOS, полный Tauri app build, native UI, длительный demo soak остаются непроверенными в этой среде. Исправление исходников не обновляет установленную у пользователя beta.4.
6. Криптографическое хранилище использует AES-GCM и локальный settings.key, не OS credential vault. Не присылать settings.key или ключи брокеров в чат.

## Как сопоставить с локальным сбоем
Нужны ОС, точная версия AEGIS, действие (Install/Start/Ping), полный текст ошибки и последние строки server.log. В текущем unified AI разделе статус содержит data_dir; новый runtime пишет server.log в этом каталоге и использует 127.0.0.1:11435. Legacy путь использует ai-runtime и порт 11434. Не удалять model cache, settings.key или trade ledger для обхода ошибок; не запускать Money для проверки сервера. После сборки исправленной версии проверить Install → Start → Ping → Stop → повторный Start → перезапуск приложения в Paper, затем отдельно demo acceptance.
